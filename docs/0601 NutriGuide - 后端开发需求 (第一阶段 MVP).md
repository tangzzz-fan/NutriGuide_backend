## NutriGuide - 后端技术开发方案 (第一阶段 MVP - 调整后)

**核心原则：**

1.  **MVP聚焦核心价值：** 第一阶段优先实现用户能直接感知和使用的核心功能（用户管理、食谱查询、饮食记录、基础推荐）。
2.  **渐进明细，风险后置：** PDF识别作为技术难点和工作量不确定性较大的部分，其完整实现可以放在MVP后期或MVP之后的迭代。MVP阶段可以先搭建基础框架，甚至先支持手动录入或简单格式导入食谱。
3.  **高内聚低耦合，预留扩展：** 在设计API、数据模型和模块时，充分考虑未来的扩展性，如PDF解析模块的接入点、更复杂推荐算法的替换等。
4.  **最佳实践与开发规范先行：** 从项目初期就强调并执行代码规范、测试策略、文档标准等，确保代码质量和团队协作效率。

**技术选型与开发规范（重点强调）：**

1.  **统一代码风格与格式化：**
    *   **TypeScript/JavaScript:** 使用 Prettier 进行代码自动格式化，ESLint 进行语法检查和风格约束（例如 Airbnb JavaScript Style Guide 或 StandardJS，团队协商一致）。
    *   **Python:** 使用 Black 进行代码自动格式化，Flake8 或 Pylint 进行代码检查（遵循 PEP 8）。
    *   **IDE集成：** 确保团队成员IDE都配置了相应的格式化和Linting插件。

2.  **版本控制 (Git)：**
    *   **分支策略：** 采用 Gitflow 或类似的简化分支模型（如 GitHub Flow）。主分支 (main/master) 保持稳定可部署，开发在新特性分支进行。
    *   **提交信息规范：** 遵循 Conventional Commits 规范，便于生成Changelog和理解提交历史。
    *   **Code Review：** 所有代码合并到主开发分支前必须经过至少一位其他团队成员的Review。

3.  **测试策略：**
    *   **单元测试：** 针对核心业务逻辑、工具函数、模块控制器和服务进行单元测试。NestJS推荐使用Jest。Python可使用unittest或pytest。
    *   **集成测试：** 测试模块间的交互，特别是API接口的正确性。
    *   **端到端测试 (E2E)：** MVP阶段可选，但应有规划。
    *   **测试覆盖率：** 设定一个合理的初始目标（如核心模块60-70%），逐步提升。

4.  **API设计规范：**
    *   **RESTful原则：** 遵循RESTful API设计风格，使用标准的HTTP方法、状态码。
    *   **接口版本管理：** 在URL中加入版本号 (如 `/v1/users`)。
    *   **统一的响应格式：** 定义标准的成功和错误响应结构（如包含 `code`, `message`, `data` 字段）。
    *   **清晰的命名：** 资源名使用复数，路径参数和查询参数命名清晰。
    *   **文档先行/同步：** 使用Swagger/OpenAPI (NestJS内置支持) 自动生成和维护API文档。

5.  **数据库设计与使用 (MongoDB)：**
    *   **清晰的集合(Collection)命名：** 例如 `users`, `recipes`, `userMealLogs`。
    *   **索引优化：** 根据查询模式合理创建索引，避免全集合扫描。
    *   **适当冗余 vs 引用：** 根据数据一致性和查询性能权衡。
    *   **避免过大的文档：** 对于无限增长的数组（如评论），考虑使用引用或分页。
    *   **ORM/ODM使用规范：** Mongoose (NestJS) 的Schema定义、模型方法、查询构造器等使用应有一致性。

6.  **配置管理：**
    *   使用 `@nestjs/config` 模块，通过 `.env` 文件管理不同环境的配置（开发、测试、生产）。
    *   敏感信息（如数据库密码、API密钥）不应硬编码到代码中，也不应提交到版本库。

7.  **日志管理：**
    *   使用统一的日志库 (如 Winston, pino) 并配置合理的日志级别。
    *   记录关键操作、错误信息、请求ID等，便于问题排查。
    *   结构化日志（如JSON格式）便于后续的日志分析和监控。

8.  **错误处理：**
    *   定义统一的错误码和错误信息。
    *   全局异常过滤器捕获未处理的异常，返回标准错误响应。
    *   避免向客户端暴露敏感的错误堆栈信息。

9.  **安全性：**
    *   输入验证：对所有来自客户端的输入进行严格校验。
    *   防止常见Web漏洞 (XSS, CSRF - 虽然API服务CSRF风险较低, SQL注入/NoSQL注入等)。
    *   HTTPS强制使用。
    *   依赖库安全扫描 (如 `npm audit`, `snyk`)。

10. **模块化与可扩展性设计：**
    *   **NestJS模块化：** 充分利用NestJS的模块（Module）、控制器（Controller）、服务（Service）、提供者（Provider）机制，实现高内聚低耦合。
    *   **接口抽象：** 对于未来可能替换或有多种实现的组件（如推荐引擎、PDF解析器），可以考虑定义接口（Interface/Abstract Class），依赖于抽象而非具体实现。
    *   **事件驱动 (可选)：** 对于解耦模块间的通信，可以考虑使用事件（如NestJS的EventEmitter模块或外部消息队列）。

---

**模块0: 项目初始化、核心基础设施与开发规范确立 (关键前置)**

*   **目标:** 搭建项目基础，**确立并宣贯团队开发规范**。
*   **主要任务:**
    *   初始化NestJS项目，定义基础目录结构。
    *   配置MongoDB数据库连接。
    *   实现全局错误处理、日志记录中间件。
    *   配置环境变量管理。
    *   **制定并文档化上述技术选型的各项开发规范。**
    *   **配置代码格式化、Linter工具，并在CI中集成检查。**
    *   配置Docker化开发环境。
*   **产出:** 可运行的基础项目骨架，完善的开发规范文档，配置好的开发辅助工具。

**里程碑B.1: 用户核心功能 (对应原B.1)**

*   **模块:** 模块1 (用户认证与画像管理)。
*   **目标:** 实现用户注册登录、画像和偏好管理的核心API。
*   **开发规范应用:** 严格按照已制定的规范进行开发、测试、Code Review。
*   **预留扩展:**
    *   用户画像字段设计考虑未来可能通过PDF解析或AI分析自动补充更多维度。

**里程碑B.2: 基础数据管理与查询 (部分对应原B.2，剥离PDF解析的复杂实现)**

*   **模块:** 模块2 (食物与食谱数据管理 - API部分及基础数据导入)。
*   **目标:** 实现食物和食谱数据的查询API，支持基础数据的导入（例如通过JSON文件或简单的后台手动录入功能）。
*   **开发规范应用:** API设计、数据库操作遵循规范。
*   **预留扩展:**
    *   **食谱数据模型 (`recipes` collection) 中预留字段**：如 `sourceType` (manual, pdf_parsed, api_import), `parsingStatus`, `originalPdfPath` 等，为后续PDF解析功能做准备。
    *   **后台管理系统接口预留**：可以先搭建一个极简的食谱录入后台界面，或者预留导入食谱数据的API接口，PDF解析功能未来可以作为这个后台的一个高级导入方式。
    *   **食物成分数据库对接**：可以先对接一个基础的食物成分库，后续可以扩展或替换。

**里程碑B.3: 初步推荐引擎**

*   **模块:** 模块3 (初步推荐系统 - 规则型)。
*   **目标:** 实现基于用户画像和偏好的规则型推荐API。
*   **开发规范应用:** 算法模块化，与NestJS API的集成方式规范化。
*   **预留扩展:**
    *   推荐引擎可以设计成可插拔的模块，未来可以方便地替换为更复杂的机器学习模型。
    *   用户反馈机制的设计要考虑为后续算法模型提供训练数据。

**里程碑B.4: 饮食记录与分析 (对应原B.4)**

*   **模块:** 模块4 (饮食记录与营养分析)。
*   **目标:** 实现用户饮食记录的增删改查及基础营养分析API。
*   **开发规范应用:** 涉及计算和数据聚合的逻辑需要重点测试。

**里程碑B.5: 动态计划校准与系统集成 (对应原B.5，不强依赖PDF解析的深度数据)**

*   **模块:** 模块5 (动态计划校准)。
*   **目标:** 实现基于用户记录和目标的校准建议API。
*   **开发规范应用:** 定时任务的实现、与用户画像数据的联动遵循规范。
*   **预留扩展:** 校准规则的复杂度和个性化程度未来可以提升。

**里程碑B.6 (MVP后期 或 MVP+): PDF食谱智能识别与导入 (原B.2中PDF核心功能的后置)**

*   **模块:** 模块2 (食物与食谱数据管理 - PDF解析与导入子模块)。
*   **目标:** 实现后台上传官方食谱PDF，系统能识别提取关键信息（食谱名、食材、步骤等），并经过人工校准后存入数据库的功能。
*   **前置条件:** 基础的食谱数据模型和后台管理框架已搭建完成。
*   **开发规范应用:** Python解析脚本的开发、与NestJS后台的集成、人工校准流程的设计遵循规范。
*   **重点:**
    *   **迭代开发:** 从支持一种或几种固定格式的PDF开始，逐步扩展兼容性。
    *   **人工校准流程是关键:** 设计友好的后台界面，方便运营人员修正和补充解析结果。
    *   **与现有食谱数据模型的整合：** 解析出的数据需要能无缝对接到已有的 `recipes` 集合中。

**最终验收 (MVP RC - Release Candidate) - 核心功能稳定，PDF识别有初步方案或基础实现**

*   **交付物:**
    *   用户能完成注册登录、管理画像。
    *   能查询食谱（手动录入或简单导入的）。
    *   能记录饮食并查看分析。
    *   能获得基础的个性化推荐和校准建议。
    *   **对于PDF识别：** 可能是一个能处理特定模板PDF的初版功能，或者是一个设计完善、预留了接口但尚未完全投入开发的模块。关键是整体架构支持未来平滑引入。
    *   所有已实现功能都经过了充分测试，遵循开发规范。

**总结调整后的策略优势：**

*   **降低早期风险：** 将最复杂的部分后置，确保项目核心能按时交付。
*   **快速验证核心价值：** 用户可以更早地使用到产品的核心功能。
*   **灵活应对变化：** 在核心功能稳定的基础上，可以根据实际情况和资源投入来调整PDF识别功能的实现深度和优先级。
*   **强调基础建设：** 将开发规范和最佳实践的落地放在项目初期，为后续所有开发工作打下坚实基础，长期来看能提高效率和质量。
